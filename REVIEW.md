# REVIEW.md

Code review findings on `app/main.py`. The starter ran happy-path requests, but contained several critical logic bugs around timezone assumptions, concurrency, rounding, and edge cases under scale.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Grace period cutoff evaluated after integer division (`minutes if minutes > 10 else 0`). R2 states punch-ins are late if strictly > 10:00 (600s) past shift start. At `09:40:01` (601s elapsed), `int(601/60)` is `10`. Checking `10 > 10` returned 0 instead of 10. | Tested with punch-in `09:40:01` for shift `09:30`. Expected 10 late minutes, received 0. | Evaluated `elapsed_seconds > 600` first. If true, return `int(elapsed_seconds // 60)`, otherwise 0. |
| 2 | `compute_late_minutes` | Naive datetime hour replacement (`punch_in.replace(hour=h, minute=m)`). If `punch_in` is UTC (e.g., 04:00 UTC = 09:30 IST), replacing hour with 9 produces 09:00 UTC, causing a -5 hour (-300 min) skew. | Deployed in UTC container: punch-in at 09:45 IST produced negative late minutes instead of 15. | Converted `punch_in` to IST (`UTC+05:30`) before comparing with IST shift start. |
| 3 | `compute_late_minutes` | Overnight shift start date attribution. Using `punch_in.replace(hour=h)` on a punch-in after midnight (e.g., 00:15 IST) pegged shift start to 22:00 of the current day (in the future) rather than the previous day. | Overnight punch-in at 00:15 IST for 22:00-06:00 shift yielded negative late minutes instead of 135. | Anchored shift start to the record's attendance date in IST (derived via R1). |
| 4 | `compute_work_hours` | Python's built-in `round()` uses Banker's Rounding (round-half-to-even) instead of Round-Half-Up required by R4. | 9,630 seconds = 2.675 hours. Python's `round(2.675, 2)` returned `2.67` instead of `2.68`. | Used `Decimal(sec)/Decimal(3600)` with `ROUND_HALF_UP` quantized to 2 decimal places. |
| 5 | `compute_work_hours` | Instant sub-second truncation was omitted. R1 specifies instants must be truncated to whole seconds before calculations. | Punch-in with milliseconds (e.g. `09:40:00.900`) altered fractional second results. | Truncated epoch timestamps to whole seconds before calculating duration. |
| 6 | `compute_overtime` | Overtime 30-minute threshold ignored. Returned raw positive minutes even when under 30. | Punch out at 18:35 for an 18:30 shift returned 5 minutes instead of 0 per R3. | Returned 0 unless elapsed minutes from shift end is $\ge 30$. |
| 7 | `compute_overtime` | Overnight shift end date placed on current calendar day instead of next day. | For 22:00-06:00 shift on 2026-07-06, punch-out at 06:40 on July 7 calculated overtime against July 6 06:00, yielding ~24 hours overtime instead of 40 minutes. | Checked if `shift_end <= shift_start`; if so, placed `shift_end` on `date + 1 day`. |
| 8 | `compute_overtime` | Offset-naive vs offset-aware datetime subtraction exception. `end` had `tzinfo=IST` while `punch_out` was naive. | Calling helper with naive UTC datetime crashed with `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Normalized both datetimes to timezone-aware IST instances. |
| 9 | `EmployeeIn` model | Missing input validation patterns. Accepted blank names/departments, invalid emails, and identical shift times. | Submitting `{"emp_code": "bad", "shift_start": "09:00", "shift_end": "09:00"}` returned 201 instead of 422. | Added regex patterns for `emp_code` (`^EMP\d{4,6}$`), email, length constraints, and validator ensuring `shift_start != shift_end`. |
| 10 | `PunchInIn` model | Missing bounds on `punched_at` (epoch ms) and enum validation on `status`. | Sending 10-digit seconds timestamp `1783310280` or `status: "ABSENT"` returned 201 instead of 422. | Restricted `punched_at` to `100000000000 <= ms <= 4102444800000` and `status` to `PRESENT | WFH | ON_DUTY`. |
| 11 | `GET /health` | Returned hardcoded `{"status": "ok"}` without verifying database connectivity. Contract requires 503 if MongoDB fails. | Stopped MongoDB daemon; `/health` still responded with 200 OK. | Added `client.admin.command('ping')` inside try/except, returning 503 if unreachable. |
| 12 | `POST /employees` | Check-then-insert race condition (TOCTOU). Concurrent creations with identical `emp_code` both passed `find_one()`. Also returned `created_at` as ISO string. | Concurrent curl requests inserted duplicate employees or failed with unhandled 500 `DuplicateKeyError`. Response `created_at` was string, not epoch ms. | Enforced database unique index on `emp_code`, caught `DuplicateKeyError` to return 409, and converted `created_at` to integer epoch ms. |
| 13 | `GET /employees` | Pagination offset skipped page 1 entirely (`skip = page * page_size`). Total count also ignored department filter. | Requesting `page=1&page_size=20` returned items 21-40. Filtering by department returned total headcount of entire company. | Fixed offset to `(page - 1) * page_size`, updated count to `db.employees.count_documents(q)`, added sort on `emp_code`, and added min/max query validation. |
| 14 | `POST /attendance/punch-in` | Crashed with 500 when employee not found. Vulnerable to race conditions on duplicate punch-ins. Returned internal `id` and ISO date string. | Punching in with non-existent `EMP9999` crashed with `TypeError` on `emp["shift_start"]`. Concurrent punches created duplicate records. | Added 404 employee check, enforced unique compound index on `(emp_code, date)` returning 409 on collision, stripped `id`, and converted `punch_in` to epoch ms. |
| 15 | `GET /attendance` | In-memory fetch (`list(find())`) and Python sort would exhaust memory on 100k docs. Missing secondary sort key on `emp_code`. Inverted date ranges returned 200. | Querying with `date_from > date_to` returned 200 with empty list. In-memory sort failed performance expectations. | Applied database-level `.sort([("date", -1), ("emp_code", 1)]).skip().limit()`, added 422 validation for `date_from > date_to`, and serialized datetimes to epoch ms. |
| 16 | Startup Lifespan | No database indexes were initialized on application start. | Queries ran via `COLLSCAN`, and uniqueness constraints were not enforced by the database. | Added FastAPI `lifespan` handler to idempotently create unique indexes on `employees.emp_code`, `attendance_logs.(emp_code, date)`, and compound query indexes. |

---

### Non-defects examined and retained:

1. **Stripping internal `_id` (`doc.pop('_id', None)`):**
   - At first glance, removing the MongoDB primary key might seem unusual, but the OpenAPI contract explicitly specifies that `_id` is an internal database detail that must never appear in API requests or responses. Removing it is intentional and correct.
2. **Leaving derived punch-out fields `None` on punch-in:**
   - Evaluated whether `work_hours`, `punch_out`, or initial history entries should be populated at punch-in. Confirmed with `DATA_MODEL.md` that punch-out fields remain `null` until punch-out occurs, and `history` is strictly an audit trail for manual regularizations (`PATCH`), not punch events.
3. **Lexicographical string comparisons on ISO dates (`$gte`/`$lte` on `"YYYY-MM-DD"`):**
   - Verified whether date strings should be converted to BSON dates for queries. Since dates are formatted as ISO-8601 calendar strings (`YYYY-MM-DD`), lexicographical ordering strictly matches chronological ordering, avoiding unnecessary timezone conversions across queries.
4. **Using `count_documents(q)` instead of `estimated_document_count()`:**
   - While `estimated_document_count()` is faster for collection-wide estimates, rule R10 explicitly states that `total` must accurately reflect the filtered subset. `count_documents(q)` is required and efficient when backed by indexes.
